# Scale Constraints — DoshMuktiV2

Same load target as V1 (`../docs/SCALE.md`): 10,000 orders/day headroom, realistic near-term load 100–1,000/day. Numbers unchanged; only the process boundary changed — checkout logic now runs inside Backend (Fastify) instead of a Next.js Route Handler.

## Load Profile

| Metric | Value |
|---|---|
| Target throughput | 10,000 orders/day |
| Average rate | ~7 orders/min |
| Peak multiplier | 3–5× (sale events, festivals, ad campaigns) |
| Peak rate | ~35 orders/min |
| Concurrent checkout users | ~200 at peak |
| Product page RPS | ~500 (browse >> buy) |

## Absolute Rules

### 1. Checkout Path — Zero Blocking Operations
`POST /checkout → stock reserve → Razorpay order create → response`, inside Backend.
- DB transaction: max 3 statements (reserve stock + create order + create payment record)
- Razorpay call OUTSIDE the DB tx — Fastify holds no DB connection during the network call
- No email in the checkout path — queued post-webhook (Resend, fire-and-forget)
- No Delhivery call in the checkout path — triggered by `payment.captured` webhook
- Target p95: < 800ms for `POST /checkout` response

### 2. Backend↔Frontend Network Hop
Splitting the app adds one HTTP round-trip Frontend→Backend that V1 didn't have (V1 called Prisma in-process via Server Actions). Mitigate:
- Backend and Frontend deployed in the **same GCP region** (`asia-south1`) — keep the hop to single-digit ms
- Frontend Server Components fetch Backend directly (no client-side waterfall) for initial page loads — see `docs/PATTERNS.md` § Server Component Fetch
- Backend responses for product listings are Redis-cached, so the extra hop mostly costs a cache read, not a DB query

### 3. Product Pages — Always Cached (in Backend)
- `listProducts()` → Redis 5 min TTL per query fingerprint
- `getProductBySlug()` → Redis 30 min TTL
- `getFeaturedProducts()` → Redis 10 min TTL
- Invalidated on `PATCH /admin/products/:id` (status/price change)

### 4. Cart — Redis Only, Never Postgres
Unchanged from V1. Cart key: `cart:{sessionId}`, TTL 7 days. `sessionId` generated by Frontend (nanoid), sent as `x-session-id` header on every Backend call.

### 5. Pincode Check — Redis 48h Cache
Unchanged. Key: `pincode:{pincode}`.

### 6. DB Connection Pool
Neon pooler (pgBouncer) unchanged. `DATABASE_URL` (pooled) for all Backend runtime queries, `DIRECT_URL` only for `prisma migrate`. Max connections from Backend: 10.

### 7. GCP Cloud Run — Min 1 Instance, Both Services
Both `Backend` and `Frontend` deploy with `--min-instances=1`. A cold start on either — Backend answering `/checkout`, or Frontend rendering the checkout page — costs an abandoned cart the same way V1's single cold start did.

### 8. Webhook Processing — Must Complete < 5s
Unchanged: signature verify sync, idempotency check 1 query, stock/order update 1 transaction, email queue fire-and-forget, return 200 before long operations.

### 9. Image Serving — R2 CDN, Never Through Either App
Images served directly from Cloudflare R2 public URL. Frontend's `next/image` uses `remotePatterns` for the R2 domain. Backend never proxies image bytes.

## Redis Key Inventory (owned by Backend)

| Key | TTL | Purpose |
|---|---|---|
| `cart:{sessionId}` | 7d | Shopping cart |
| `pincode:{pincode}` | 48h | Serviceability cache |
| `products:featured:{limit}` | 10m | Featured products |
| `products:list:{hash}` | 5m | Paginated listing |
| `product:slug:{slug}` | 30m | Product detail |

Hash for listing key: `sha1(JSON.stringify({ purpose, sort, page, limit }))`.

## What NOT to Cache

- Order data, stock quantities — always Postgres, must be accurate
- Admin data — skip Redis entirely
- Webhook events — idempotency via Postgres `UPDATE WHERE`, not Redis

## Postgres Index Checklist (unchanged from V1 schema)

- `Product(status, category)`, `Product(status, featured)`, `Product(slug)`
- `Order(status, createdAt)`, `Order(orderNumber)`, `Order(reservedUntil)`
- `ProductVariant(sku)`
- `StockMovement(variantId, createdAt)`

Before adding a new query in a hot path: `EXPLAIN ANALYZE` it, confirm Index Scan not Seq Scan.

## Load Testing Before Launch

```bash
# Point at Backend directly, then again through Frontend's Server Component fetch path
k6 run --vus 50 --duration 60s scripts/load-test-checkout.js
```

Target: zero errors, p95 < 1s end-to-end (including the Frontend→Backend hop), no Postgres deadlocks.
